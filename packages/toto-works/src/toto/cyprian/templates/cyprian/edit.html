{% comment %}---- the writing toolbar ---- Ours, not TipTap's: TipTap ships no UI at all, which is the point of using it. Every button runs a command through `cmd()` and asks `isActive()` what the caret is in, so "is this on" and "turn this on" cannot disagree — which is exactly how a toolbar ends up lying about the selection. It is sticky because a document is taller than a screen and a formatting control you have to scroll to is a control you stop using. {% endcomment %}
{% comment %} Size and colour are CLASSES, never inline styles: the server strips `style` everywhere in this suite, so an inline-style mark would vanish on the first save. See sanitize_html.py.{% endcomment %}
{% comment %} Table controls appear only when the caret is in a table. Eight buttons that do nothing most of the time is the clutter this editor exists to avoid.{% endcomment %}
{% comment %}---- the canvas ---- ONE editor, for the whole document. No sections to add, order or delete — a heading in the body is the structure, and it is one keystroke rather than a button, a level and an ordering to manage. The sheet is A4 and the page boundaries are DRAWN where the paginator measured them: the canvas stays one continuous element, because splitting it into real page elements would mean moving nodes around under a live ProseMirror view, which loses the caret. `document.css` draws the gap so it reads as the next sheet. {% endcomment %}
{% comment %} ---- source view ---------------------------------------------------- The document IS one XML file, so this is not a debug panel: it is the document, in the form it is stored and backed up in. ACE because the rest of this platform edits text in ACE, and because a textarea over a 2,000-line document is not editing. Applying goes through the SERVER's parser (document_format.loads) rather than a second one written in JavaScript. One parser, one set of rules, one place a malformed file is explained. -------------------------------------------------------------------{% endcomment %}
